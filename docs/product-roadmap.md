# Product roadmap — decisions across concurrent Git work

ClocGit coordinates concurrent changes and turns them into a smaller set of explicit decisions. Its primary object is a reviewed choice over immutable proposal revisions, relationships, constraints and evidence. The result is an actual Git composition applied only while its reviewed basis and canonical head still match.

The workflow preserves **Intent → Proposal → Decision → Implementation → Evidence**. Git remains authoritative for code. ClocGit records coordination, provenance, decisions and bounded evidence; any ordinary human, agent, bot, CI system or Git client can produce work.

## Relationship to code-review products

There is overlap with PR review: diffs, discussion, summaries, approvals and check results. The distinguishing workflow is deciding across concurrent work: whether two implementations can share one implementation reference, which alternative to choose, whether individually passing changes interact, which exact composition to apply, and when prior evidence or authorization has become stale.

For example, a reviewer can inspect A and B separately and approve each. ClocGit also constructs A+B and may observe a failure that neither individual candidate exhibits. It then presents the interacting choices, preserves both histories and requires a decision on that exact composition. A summary or review comment cannot authorize a stale or different Git tree.

CodeRabbit's PR-review workflow is a useful point of comparison, and a review assistant could supply additional declared findings. This roadmap does not claim a complete audit of CodeRabbit's current features. ClocGit's product goal is decision compression with an immutable authorization and evidence protocol, rather than an AI code-reviewer implementation. Semantic suggestions, if introduced, remain hints.

The local retry-enabled demonstration has eight proposals and two derived review decisions, with one preceding context clarification. Those finite results demonstrate one scenario; they are not a general compression guarantee or proof of semantic correctness.

## Scope and status

This is the full product plan for the nineteen requested domains. It is not a declaration that all nineteen are delivered. The current build is a native Git/Cloudflare Artifacts prototype with locally verified mechanisms, one configured owner, finite trusted validation profiles and a minimal decision-first interface. Live Cloudflare account integration remains unverified. GitHub/GitLab connectors, organizational identity and a general CI fleet are not implemented.

The current delivery extends and verifies the native foundation and exposes explicit capability status. Work outside that bounded delivery remains planned. No credentials, production resources or external integrations are provisioned by this roadmap.

Use the [capability registry](capabilities.md), exposed by authenticated `GET /api/capabilities`, for individual claims and their exact test references. Its statuses mean:

- **Supported:** the named, bounded behavior is implemented and backed by identified checks. A local test does not establish live deployment behavior.
- **Partial:** some of the requested behavior exists, with named missing boundaries.
- **Experimental:** an implemented path has explicitly limited validation or deployment confidence.
- **Unsupported:** there is no supported operational path for the named behavior.

Broad domains below are mostly partial because each includes substantially more than the current prototype. Historical verification is recorded in the [native workflow evidence](evidence/native-workflows-verification.json); it is not evidence that later source changes have already passed.

## Delivery order and dependency gates

The nineteen domains are product coverage areas, not nineteen independent implementation projects. Build in this order, with the six core invariants retained at every gate:

| Stage | Deliverable | Dependencies and exit gate |
|---|---|---|
| **F — Foundation** | Ordinary Git ingress, registered repositories/forks, immutable proposals/revisions, native MR lifecycle and exact reviews, bounded evidence, decision basis and true Git CAS, recoverable journal, truthful capability registry | Prove duplicate/out-of-order ingress, unknown provenance, force-push/deletion, exact review/check binding, source/head/basis staleness and uncertain-write recovery. Git must remain cloneable with the platform stopped. Establish this deterministically before adding semantic analysis. |
| **C — Coordination** | Typed revision relationships, dependency DAGs, actual compositions, decision groups, explicit single/batch convergence and an exact reviewed merge queue | Requires F. Individually passing candidates must also be validated together. Dependencies pin revisions; stale tickets require renewed review. Unknown interactions remain conventional review. |
| **U — Understanding** | Broader task/context compilation, assumptions, minimal material clarification, existing-work retrieval and bidirectional provenance | Requires F's immutable sources and C's decision inputs. Retrieved, declared, observed and inferred items stay distinct. Unanswered questions become explicit unresolved assumptions rather than an indefinite producer lock. |
| **S — Scale** | Scope/subsystem/symbol/dependency indexes, bounded asynchronous analysis, queue scheduling, cross-repository contract validation and measured performance | Requires correct F/C/U semantics. Benchmark candidate filtering and latency against a representative workload. Cross-repository transitions use explicit recovery; they are not silently treated as atomic. |
| **P — Production** | Multi-user authorization, scoped credentials, hardened runner fleet, integrations, independent audit retention/anchors and live Cloudflare verification | Requires demonstrated safety/recovery and deployment-specific evidence. Verify account permissions, native event delivery, remote lease races, container isolation and restart behavior before claiming production readiness. |

Production security starts with F's authenticated writes and isolated execution; P expands it into an organizational boundary. Some current prototype slices already exercise C and U, but this does not bypass the earlier gates or establish production coverage.

## Model accommodations before broader workflows

These are proposed additions to the existing model, not statements that the current API implements them.

### Separate proposals, MRs and target revisions

A Proposal is an intent/rationale history. A ProposalRevision is an immutable candidate. An MR is a delivery/review conversation targeting a particular repository/ref. Give each a stable identity and preserve an explicit association rather than deriving a permanent one-to-one relationship from a source branch.

Allow several MR histories to refer to a proposal or pinned revision. Each MR retains its own source, target, lifecycle, approvals and discussion. Closing, abandoning or retargeting one MR does not change another MR or erase the proposal. All policy applicable to the selected delivery must be checked; another MR's approval cannot be borrowed accidentally.

Retargeting appends an MR event with the old/new target and immutable target heads. It refreshes target-dependent merge base, context, composition, evidence and review basis; prior records remain historical. Supporting another protected target requires an explicit canonical scope and the same serialization/CAS protocol, not a loose change to `target_ref`.

Keep lifecycle and disposition separate. Draft/ready describe review readiness; open/closed/merged describe delivery history. Applied/deferred/rejected/superseded describe immutable revision decisions. Supersession records the successor revision and rationale. Deferred means unresolved or intentionally postponed, not rejected. Current applied/deferred history can be migrated without rewriting its records.

### Typed immutable relationships

Every edge pins `from_revision`, `to_revision`, `basis`, `analyzer_version` or declaring actor, and evidence references. Define directions explicitly:

| Type | Meaning and required guard |
|---|---|
| `implementation_equivalent` | Exact observed code identity may reuse an implementation; it preserves intent/provenance. Broader semantic equivalence stays a hint. |
| `alternative` | Revisions offer competing choices for a specific decision scope. A declaration is labeled as such. |
| `requires` / existing `depends_on` | The source revision requires the pinned target revision/capability. Check cycles and transitive eligibility. Normalize aliases through a versioned schema. |
| `blocks` | The source is an explicit blocker for the target under a stated policy or unresolved decision. A descriptive hint does not itself authorize rejection. |
| `supersedes` | The source replaces the pinned target within a declared scope. Preserve the target and its disposition history; do not infer replacement from a newer timestamp. |
| `conflicts_with` | Code or bounded behavior conflicts with the target. Explain observed evidence versus declared/inferred concern. Unknown semantic conflicts escalate. |
| `compatible_candidate` | There is a reason to attempt composition. Actual composition validation determines the bounded claims for the resulting tree. |
| `unknown` | Analysis does not establish another relationship. Missing edges are not proof of compatibility. |

Do not overload MR dependencies as every relationship type. Application guards must use the relevant pinned dependency closure, while decision grouping uses unresolved alternatives/conflicts and their explicit scope. A changed edge creates a new version and invalidates a basis that depended on it.

### Version decisions, evidence and dispositions together

Expand the reviewed basis as features arrive: selected proposal revisions; participating MR versions/targets/reviews; relevant typed edges and dependency closure; constraints and policy versions; context/assumptions; exact compositions/evidence and their eligibility; observed canonical/source heads. New relevant inputs require new review rather than silent reuse of authorization.

Evidence run states are versioned events over exact immutable inputs. Completed results are immutable. Staleness changes eligibility, never the historical result. Required trusted evidence must cover the actual selected composition; external CI or human reports keep their declared source and cannot assert platform authority.

A Decision records the reviewed basis, actor, rationale and explicit consequences. Per-revision/MR disposition records reference that decision and exact implementation when applied. Rejected and superseded are future authorized outcomes with explicit reasons, not aliases for closing an MR. Reverting code produces a new reviewed inverse; it does not erase an earlier applied decision.

## Acceptance and delivery boundaries

The foundation must preserve the existing adversarial cases: duplicate implementations with separate histories, independent work, competing choices, individually valid but interacting changes, unknown provenance and evidence that becomes stale after canonical movement. Ordinary clone/fetch/push, exact source/head/basis races and conservative crash recovery are mandatory gates.

The competition scenario remains bounded: one baseline application, at least two repositories, four or five concurrent producers and one or two meaningful review decisions. Count the preceding clarification separately. Publish immutable inputs and the finite checks behind the result. Reducing the displayed count by dropping unknown work, auto-resolving alternatives or accepting stale evidence is a failure.

For each subsequent delivery, update the capability registry with the implemented scope, explicit exclusions, exact verification and deployment status. Use targeted regression checks for changed behavior, then the appropriate existing integration/build checks. A plan entry or passing mock test does not move a live capability to supported.

The primary metric remains human review decisions divided by candidate proposals. Pair it with incorrect duplicate classifications, accepted stale evidence, reversals of automatic actions, handled CAS failures, traceable rationale, analysis latency and comparisons avoided. Include assumptions and elapsed work-to-decision time as the workflow expands. Do not optimize compression at the expense of false convergence.
